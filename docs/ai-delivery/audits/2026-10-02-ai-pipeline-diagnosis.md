# AI 链路性能诊断（2026-10-02）

阶段 3 的第一步：先量后改。本文记录**可复跑的诊断方法**、静态发现与实测结果。
所有结论都指明证据位置；未实测的部分明确标注为未知。

## 1. 方法与工具

- 工具：`scripts/diagnose-ai-latency.mjs`（只读，可重复；密钥只从 `.env` 读取，绝不打印；只打印长度/token/耗时，不打印正文）
- 用法：`node scripts/diagnose-ai-latency.mjs --runs=2`，或显式传真实脱敏讲义路径
- 纪律：`--runs` 限制调用次数，避免重复产生付费副作用；失败即停，不盲目重试

## 2. 静态发现（读代码即可确认）

| #   | 发现                                                                       | 证据                                                                               | 影响                                                                         |
| --- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| S1  | 两个 provider 客户端**都没有设置超时**，调用时也没有传 `timeout`           | `src/lib/ai/vision.ts:24`、`src/lib/ai/text.ts:24`、`src/lib/ai/batch-feedback.ts` | OpenAI SDK 默认超时 600s：provider 挂死时单请求可占住并发槽 10 分钟          |
| S2  | 未限制重试次数                                                             | 同上（SDK 默认对 408/409/429/5xx 自动重试 2 次）                                   | 最坏情况单请求 = 3×600s，远超全局队列 60s 超时语义，用户侧表现为长时间无响应 |
| S3  | 视觉模型一次吃下最多 5 张图（单次非流式）                                  | `summarize/route.ts` `MAX_IMAGES_COUNT = 5`、`vision.ts:63-84`                     | 多图会线性抬高 vision 阶段耗时；是否需要拆分取决于实测（见 §4）              |
| S4  | 批量反馈按 40 学生/批**串行**调用，且最多重试 3 次                         | `batch-feedback.ts:57 / 125-134 / 307-311`                                         | 60 学生 = 2 次串行 AI 调用；失败重试会成倍拉长总时长                         |
| S5  | 图片压缩：桌面 1920px/0.5MB/q0.85，移动 1280px/0.4MB/q0.8，二次降级 0.25MB | `image-compress.ts:21-27, 85-89`                                                   | 载荷已受控；进一步优化收益取决于真实讲义分辨率分布                           |
| S6  | 全局并发槽 5、队列 100、等待上限 60s                                       | `summarize/route.ts` 常量区                                                        | 与 S1/S2 组合时，槽位可能被慢请求长期占用                                    |
| S7  | SSE 协议在首 chunk 内联 `__META__`，错误转 `__ERROR__` 并保留原 code       | `summarize/route.ts` 流包装段                                                      | 前端已能区分错误类型；T-002 又追加了 `billingState`，不改旧字段              |

## 3. 实测结果

### 3.1 原配置不可用（凭据问题，非代码问题）

原 provider 配置下 `node scripts/diagnose-ai-latency.mjs --runs=2`：

| 阶段   | 实测                    | 说明                    |
| ------ | ----------------------- | ----------------------- |
| vision | HTTP **402**，195–284ms | 硅基流动侧余额/额度不足 |
| text   | HTTP **401**，75–129ms  | DeepSeek 密钥无效/过期  |

### 3.2 换用智谱 GLM Coding Plan 后的真实基线

端点与模型（已核实为可用）：OpenAI 兼容端点 `https://open.bigmodel.cn/api/coding/paas/v4`
（注意：标准 `/api/paas/v4` 返回 429「余额不足或无可用资源包」，套餐只覆盖 coding 端点）；
`glm-5.3-flash` 支持 image 输入，可同时充当 vision 与 text。样本同为
`public/images/feature-feedback.png`（145KB，**营销图，仅作载荷代理**；真实讲义载荷更大，见 §3.4）。

| 阶段                    | 中位耗时      | token / 备注                                   |
| ----------------------- | ------------- | ---------------------------------------------- |
| vision（glm-5.3-flash） | 18,378 ms     | prompt 1455 · completion 634–871 · JSON 可解析 |
| text 首 token           | 1,106 ms      | glm-5.3，SSE 流式                              |
| text 总时长             | 10,078 ms     | 同上                                           |
| **两阶段合计**          | **28,456 ms** | vision 占 65% —— **瓶颈在视觉阶段**            |

### 3.3 A/B：关闭推理模型的思考（`AI_EXTRA_BODY_JSON={"thinking":{"type":"disabled"}}`）

| 阶段              | 思考开启  | 思考关闭     | 变化             |
| ----------------- | --------- | ------------ | ---------------- |
| vision            | 18,378 ms | **4,357 ms** | **−76%（4.2×）** |
| vision 完成 token | 634–871   | 76–115       | −87%             |
| text 总时长       | 10,078 ms | **2,607 ms** | **−74%**         |
| text 首 token     | 1,106 ms  | 1,024 ms     | 基本不变         |
| **两阶段合计**    | 28,456 ms | **6,964 ms** | **−75.5%**       |

两种模式下 `finish_reason=stop` 且 JSON 均可解析 —— 对「读图抽 JSON」这类短任务，
思考 token 纯属浪费。**未做人工内容质量评审**，因此这里只宣称「结构有效 + 延迟下降」，
不宣称「识别质量不变」。

### 3.4 尚未测量的项（不猜测）

- 真实讲义载荷（压缩后 0.4–0.5MB）下的 vision 耗时曲线：本样本 145KB 偏小，数值偏乐观
- 多图（2–5 张）的 vision 耗时增长曲线：S3 的拆分决策依赖它
- 批量反馈单批耗时与跨批并行的安全并发度：S4 依赖它
- ~~8B→32B 升级阈值~~（**已过时，2026-10-03**）：该条目针对旧硅基流动 Qwen3-VL-8B/32B
  路径；现网视觉模型已切换为智谱 `glm-5.3-flash`（§3.2），若识别质量不足应评估
  智谱侧更大的视觉模型，而非 Qwen 32B。保留「识别失败率需真实样本测量」这一点。

## 4. 已实施的改进

| 改进                                                                                     | 依据                     | 默认行为                                                   |
| ---------------------------------------------------------------------------------------- | ------------------------ | ---------------------------------------------------------- |
| vision / text / batch 客户端显式 `timeout` + `maxRetries`                                | S1/S2（最坏等待 3×600s） | 生效，无行为变化（仅上限收敛）                             |
| provider / baseURL / model 全部改为环境变量驱动（`VISION_*` / `TEXT_*`，旧变量名仍兼容） | 换 provider 需要改代码   | 不设变量时与改动前完全一致                                 |
| 新增 provider 无关的附加请求体开关 `AI_EXTRA_BODY_JSON`                                  | §3.3 实测 −75.5%         | **默认不注入**（硅基流动的 Qwen3-VL 不认 `thinking` 字段） |

仍然待实测后再决定的项：vision 多图拆分（S3）、批量跨批并行（S4）、压缩阈值分级（S5）、
真实讲义识别失败率（~~8B→32B 升级阈值~~已随 provider 切换过时，见 §3.4）。

## 5. 对后续阶段的影响

- 阶段 3 的「延迟前后对比数字」**已交付**：见 §3.2 基线 与 §3.3 的 −75.5% 对比。

  代码内默认值仍保留硅基流动 + DeepSeek 官方作为无环境变量时的兜底。
- 阶段 4（S04 无 Office 交付）是纯客户端产物层，不依赖 AI 凭据。
- 建议后续动作：把 §3.4 的剩余补测（真实讲义载荷、多图曲线、批量并发、失败率）纳入
  S03/S04 之后的专项，或在下一次拿到真实样本时用同一脚本补齐。
